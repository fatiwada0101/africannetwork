## What To Build

### Approach: Double-Submit Cookie Pattern

Since the admin auth is being moved to JWT cookies (see 1.2), CSRF protection uses the double-submit cookie pattern:

1. Server sets a `csrf_token` cookie (random token)
2. Client reads cookie and sends token in `X-CSRF-Token` header
3. Server verifies header matches cookie

```javascript
// Middleware or per-route check
function validateCsrf(request) {
  const cookieToken = parseCookie(request, 'csrf_token');
  const headerToken = request.headers.get('X-CSRF-Token');
  if (!cookieToken || cookieToken !== headerToken) {
    return new Response('CSRF token mismatch', { status: 403 });
  }
  return null; // Valid
}
```

### Exemptions

These routes should **NOT** have CSRF protection:
- `/api/webhook/flutterwave` — Flutterwave server-to-server (uses `verif-hash`)
- `/api/cron/expire-vouchers` — Vercel cron (uses `CRON_SECRET`)
- All GET/HEAD/OPTIONS requests
